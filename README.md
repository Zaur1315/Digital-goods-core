# Marketplace digital goods — stage 2

Серверное ядро маркетплейса цифровых товаров на PHP 8.3, PDO и SQLite. Один заказ содержит до 50 позиций; цена и поставщик фиксируются в момент создания. Оплата и поставщики — локальные заглушки.

## Запуск

```bash
php -S 127.0.0.1:8080 -t public
```

Для чистого запуска удалите только тестовую БД или задайте другой файл:

```bash
DATABASE_DSN=sqlite:/tmp/marketplace.sqlite php -S 127.0.0.1:8080 -t public
```

Создание и оплата заказа:

```bash
curl -s -X POST http://127.0.0.1:8080/orders \
  -H 'Content-Type: application/json' \
  -d '{"customer":"player@example.com","items":[{"sku":"GAME-100"},{"sku":"GAME-200","quantity":2}]}'

curl -s -X POST http://127.0.0.1:8080/webhooks/payment \
  -H 'Content-Type: application/json' \
  -d '{"order_id":"<ORDER_ID>","payment_id":"pay-1","status":"succeeded"}'
```

Повтор webhook с тем же `payment_id` безопасен. Старый формат первого этапа `{"sku":"GAME-100","customer":"..."}` также поддерживается.

## Сценарии проверки

Частичный сбой: поставщик A выдаст `GAME-100`, B трижды откажет для `GAME-200`. После webhook подождите 2 секунды, вызовите `POST /worker`, ещё через 3 секунды вызовите worker снова:

```bash
SUPPLIER_B_MODE=fail DATABASE_DSN=sqlite:/tmp/partial.sqlite php -S 127.0.0.1:8080 -t public
```

Итог заказа — `partially_fulfilled`: первая позиция `delivered`, вторая `refunded`. Поле `money` показывает, например, `paid: 4998`, `delivered: 1999`, `refunded: 2999`, `balanced: true`.

Недобросовестный поставщик задаётся отдельно для A/B или сразу для всех:

```bash
SUPPLIER_A_MODE=timeout php -S 127.0.0.1:8080 -t public
SUPPLIER_A_MODE=duplicate php -S 127.0.0.1:8080 -t public
SUPPLIER_A_MODE=wrong php -S 127.0.0.1:8080 -t public
```

- `timeout` сохраняет фактическую выдачу, затем отвечает ошибкой. Сверка по стабильному ключу находит код, поэтому второй код не запрашивается.
- `duplicate` на первой попытке возвращает ранее выданный код. Уникальный индекс отклоняет его, после подтверждённого расхождения создаётся новая попытка и выдаётся свободный код.
- `wrong` возвращает код другого SKU. Такой код не попадает покупателю; после трёх ответов позиция автоматически возвращается.
- `fail` ничего не выдаёт и завершает позицию возвратом после трёх попыток.

Зависшие после аварии задачи подхватывают `POST /reconcile` и `POST /worker`. `reconcile` читает отдельно сохранённый факт поставщика и чинит расхождение без ручного изменения данных.

## API

- `POST /orders` — создать заказ: `{customer, items: [{sku, quantity?}]}`.
- `GET /orders/{id}` — позиции, коды, статусы и денежная сверка.
- `POST /webhooks/payment` — идемпотентно подтвердить оплату.
- `POST /worker` — обработать очередь, опционально `{limit}`.
- `POST /reconcile` — восстановить зависшие выдачи и показать расхождения.
- `GET /queue` — число `queued`, `processing`, `done`, `failed`, `delivered`.
- `GET /orders/{id}/at?at=<ISO-8601>` — состояние заказа и денег на момент времени.
- `GET /reports/money?from=<ISO-8601>&to=<ISO-8601>` — денежные итоги из журнала событий.
- `GET /catalog?limit=50&offset=0` — каталог.

## Инварианты и восстановление

`deliveries.code` уникален глобально, а `deliveries.item_id`, `refunds.item_id`, `payments_v2.order_id` и event/payment idempotency keys уникальны на уровне БД. Поэтому параллельный или повторный вызов не создаёт вторую выдачу, оплату или возврат. Выдача и изменение позиции фиксируются одной локальной транзакцией.

У поставщика факт выдачи (`supplier_issues`) отделён от полученного приложением ответа. После таймаута приложение сверяет факт по ключу конкретной попытки. Подтверждённый неверный/занятый код отбрасывается; только после этого разрешается следующий ключ попытки.

`domain_events` — дополняемый журнал. Срез на дату и отчёт за период строятся из него, а не из текущих строк заказа. Для завершённого оплаченного заказа всегда выполняется:

```text
paid_cents = delivered_cents + refunded_cents
```

Во время обработки `balanced` может быть `false`: деньги уже получены, а позиции ещё находятся в очереди. В конечном состоянии он обязан стать `true`.

Лимит задаётся `SUPPLIER_RPM` либо `SUPPLIER_A_RPM`/`SUPPLIER_B_RPM` (по умолчанию 60). Счётчик обновляется атомарно по минутным окнам. При исчерпании лимита worker оставляет задачи в durable-очереди. Оплаченные задачи имеют приоритет 100; неоплаченные поставщику не отправляются.

## Проверки

При запущенном сервере:

```bash
php tests/concurrency.php http://127.0.0.1:8080
```

Скрипт посылает 20 одинаковых payment webhook параллельно и проверяет одну оплату, одну выдачу на позицию, отсутствие повторяющихся кодов и денежный баланс.

Фактически затраченное время: около 15 минут. Готов на звонке внести небольшое изменение в код и объяснить решения.
